# 创建规则时自选入口端口与连续范围设计

日期：2026-11-16

## 意图

企业独占入口节点上的客户在创建规则时可以继续自动分配，也可以指定一个入口端口或一个连续端口段。端口段内所有端口转发到同一个目标主机和目标端口，仍按一条规则计量、限速、扣费和展示。RelaDock 只做 TCP/UDP 透明转发，不终结或托管客户 VPN/代理协议。

## 本次范围

- 只实现新规则创建；已有规则的入口更换仍需未来的暂停、applied ACK、候选隔离和退休组状态机。
- 自选端口只对 `dedicated-tenant` 节点及其归属企业开放。共享节点与 `dedicated-rule` 节点继续自动分配单端口。
- 省略 `listenPort` 与 `listenPortEnd` 时保持现有自动分配；只传起始端口视为单端口；只传结束端口拒绝；两者都传表示闭区间。
- 起止必须位于 `1-65535`，起始不大于结束；首期每条规则最多 4096 个数字端口，单节点活动精确端点最多 10000 个，`both` 按 TCP 与 UDP 分别计入端点数。
- 每个节点具有按协议区分的客户允许端口池。迁移和新节点默认 TCP/UDP 都是 `20000-60000`；低端口不因升级自动开放。本次不增加端口池管理界面。
- 数据库继续以 `(node, address, protocol, port)` 精确占用作为最终冲突裁决。范围内任一冲突使整个事务回滚。
- `relay_rules.listen_port` 保持起点并新增 `listen_port_end`；现有规则回填为起止相等。
- 配置 schema 4 携带 `listenPortEnd`。控制面只向最新心跳声明范围能力的 Agent 租出含范围的配置；旧 Agent 不得到降级配置，规则保持等待交付。
- Agent 校验范围与精确 allocation 完全一致；nftables 用区间匹配，tc 对整个范围使用同一规则 mark/class，来源记录继续保存实际命中的精确入口端口。
- 删除规则沿用现有逐端点隔离与安全退休，不提前复用已下发范围中的任何端点。
- 控制台根据所购套餐的资源模式启用端口模式；不满足独占节点时只能自动分配。列表、成功提示和编辑只读摘要显示 `start-end`。

## 兼容与安全边界

- 旧 API 调用、旧单端口规则和现有计费周期保持兼容。
- 请求幂等摘要包含端口请求；同一幂等键不能改用另一个范围。
- 没有 applied ACK 时仍不得显示“运行中”；目标 TCP 探测仍不代表端到端健康。
- Agent 的本机监听冲突只做只读预检并拒绝应用，不停止外部服务；本次至少保留现有 nft check/apply 失败关闭边界。
- 生产先迁移控制面并发布兼容 Agent 包；未升级 Agent 的范围规则只能等待。实际 Agent 升级和独立 VPS/HY2 跳端口生产验收单独记录，不伪造完成。

## 验证

1. 迁移保持现有规则为单端口并创建默认端口池。
2. 独占租户创建 `40000-41000/udp` 得到一条规则和 1001 个精确 allocation。
3. 共享/他租户/池外/反向/超长范围拒绝且无部分写入。
4. 重叠范围和 `both` 任一协议冲突均原子失败；幂等重试保持一致。
5. schema 4 对 allocation 缺口、额外端口、重复端口和旧 Agent 交付失败关闭。
6. nftables 与 tc 对范围使用同一规则级计数、额度和 class，精确来源 manifest 仍可归属命中端口。
7. 控制台模式切换、请求载荷、范围显示和共享节点禁用行为有浏览器单元测试。
8. PostgreSQL、Go race、Node、静态检查、Linux 构建和部署前配置检查通过；Linux 隔离转发及真实 VPS/HY2 验收未执行时明确标注。
