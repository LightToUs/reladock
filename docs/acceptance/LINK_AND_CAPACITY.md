# 真实链路、VPN 客户端与容量验收

本清单用于获授权的生产式 Linux 环境。它不购买服务器、不打开云防火墙、不部署客户协议服务，也不把 TCP 目标可达或配置 `applied` 当成端到端健康。每种节点规格、内核、网卡和线路都要单独执行；结果不能外推到其他地区或供应商。

## 拓扑与隔离

至少使用三个相互独立的主机/网络位置：

```text
外部测试客户端  →  RelaDock 入口公网 IP:分配端口  →  专用测试落地:测试端口
```

- 客户端不得运行在入口节点或同一私网，否则可能绕过公网入口、防火墙、NAT 和实际回程。
- 测试落地只能运行短时 TCP/UDP echo、iperf3 或客户自有协议测试实例；限制来源为入口 SNAT 地址，结束后关闭监听和临时防火墙规则。
- 入口使用与生产相同的 systemd apply 单元、专用 egress 租约、SNAT、nftables/tc/conntrack 工具和 offload 策略。不要在验收中临时放宽 RelaDock 的安全门禁。
- 每条规则独立设置带宽和流量额度。不得把两条规则的总和当成共享套餐，也不得用节点声明容量冒充保证带宽。

## 验收前记录

保存以下非密钥信息：发行版本和 SHA-256、三台主机提供商/地区/规格、内核和 iproute2/nft/conntrack 版本、入口接口名/ifindex/namespace/alias/MTU、shaping 租约摘要、云安全组摘要、测试规则 ID/协议/入口端口/目标、每规则带宽/额度/周期、开始时间和操作者。不得记录客户 UUID、Reality 私钥、密码、Agent 私钥、会话或安装凭证。

先确认：

- 后台 Agent 联系为近期、证书有效、当前 generation 已 `applied`；这些只允许开始测试，不代表测试通过。
- `nft`/`tc` readback 与 Agent last-good 一致，无 flowtable；GRO/GSO/TSO/LRO 前置条件满足。
- Prometheus 中数据库、worker、当前交付、事件和 retirement 无未解释错误。
- 入口和落地的系统时间同步，磁盘有足够 WAL 空间，测试期间保存日志但不抓取客户业务载荷。

## TCP 与 UDP 转发

为 TCP、UDP、`both` 分别建立独立规则并执行：

1. 从外部客户端连接入口公网 IP 和平台分配端口，确认测试落地收到入口 SNAT 地址，而不是客户端源地址。
2. TCP 发送带随机序号的多包数据并逐字节回显；覆盖短连接、并发连接、至少一个超过常规 idle 周期的长连接、断开后重连、大包/小包和客户端主动/服务端主动关闭。
3. UDP 使用带序号和随机内容的应用层回显，统计发送、收到、重复、乱序和丢失；仅创建 UDP socket 或入口节点到目标的探测不算通过。
4. `both` 必须在同一入口数字端口分别完成 TCP 和 UDP，证明两种传输是独立资源但规则语义一致。
5. 使用不存在的入口端口和另一企业/规则端口做负向测试，确认没有宽范围捕获或跨规则转发。

记录每次测试的 UTC 时间、字节/包、时长、连接数、结果和客户端/落地日志摘要。原始业务载荷不进入证据包。

## VPN 客户端透传

RelaDock 不终结 VLESS、VMess、Reality、HY2、TUIC、WireGuard 等协议。对客户已有配置，只把：

- `server` 改为入口节点公网 IP 或稳定域名；
- `server_port` 改为该规则分配的入口端口。

UUID、密码、Reality public key/short ID、SNI、uTLS fingerprint、flow、TLS 和落地协议配置仍属于客户落地服务，RelaDock 不生成或修改。TCP 型协议建立 TCP 规则；实际依赖 UDP 的协议建立 UDP 或 `both`，不能因客户端配置里出现 `xudp` 就猜测外层一定是 UDP。

至少从两种真实外部网络各完成一次握手、数据请求、持续传输和重连。保存客户端成功/失败时间与匿名化错误类别，不上传订阅文件或协议密钥。成功只证明本次客户协议样本，不代表所有 VPN 客户端兼容。

## 每规则带宽与容量

- 为规则 A 设置较低上限，单独运行足够长的 TCP/UDP 吞吐测试，避开启动突发，以 tc class 实际字节和客户端测量核对平均上限。
- 为规则 B 设置不同上限并单独重复；随后 A、B 并发，确认各自仍受自己的 class 上限约束，而不是共享企业带宽桶。
- 双向分别测试，并验证同一规则的上传与下载共用一个双向合计上限。不要把单方向结果相加后误认为两个独立额度。
- 逐步增加并发连接、规则数、包速率和吞吐，记录 CPU、软中断、内存、丢包、延迟、conntrack 使用、nft/tc 统计和 WAL 增长。达到预设错误/延迟/资源阈值即停止；最后一个稳定点才是本规格的验收容量，不是销售保证。
- MTU、分片、IPv4 路径、云厂商限速和跨境线路分别记录。不得用一次峰值测速宣传持续 1 Gbps。

## 流量、额度与续期边界

每条规则从新的计量周期和已知基线开始。分别产生确定大小的上行、下行和双向流量，等待 WAL ACK 后核对：入口 nft/tc 统计、Agent 本地累计、平台 usage report、周期汇总和剩余额度。允许解释协议开销、重传和 hook 计数差异，但差异必须有记录，不能手工改账抹平。

验证 A 的流量不会消耗 B 的额度；A 达到额度或到期后由内核阻断，B 继续；Agent/控制台短时离线时本地 WAL 继续，恢复后按 epoch/sequence 幂等补传且不重复。续期必须产生新周期归属，迟到旧周期报告不得扣新周期。开发绕过模式不得用于商业验收。

## 暂停、删除、故障和恢复

- 暂停：观察新连接停止、已有连接的真实行为和保留端口；记录从操作到 applied 的时间，不承诺即时断开。
- 删除：等待 schema-2 quarantine、精确 conntrack purge、proof/report/ACK 和 allocation 释放；在 ACK 丢失、Agent 重启和重复报告下证明可恢复。未完成前同端口不得复用。
- 回滚：注入候选配置失败，确认旧规则恢复、候选端口 guard 保留、计量基线不重置。
- 重启：分别重启 Agent、入口 VPS 和控制服务，验证 journal/WAL/updater/PKI 恢复；不能删除状态目录来获得“成功”。
- 控制中断：入口保留最近有效内核策略，WAL 有界积压；恢复后无重复扣量。WAL 满或状态不确定应失败关闭/冻结，而不是继续无计量转发。
- 节点退役：按 [安全退役验收](SAFE_RETIREMENT.md) 完成维护、排空、证明和身份撤销，不使用强制 SQL/flush。

## 通过门禁与证据包

每项标记通过、失败或未执行；未执行不能写“通过”。证据包至少包含：拓扑、时间、版本/摘要、匿名化规则参数、命令版本、测试工具原始摘要、Prometheus 时间窗、nft/tc/conntrack/WAL/平台记录的相关摘要、差异解释、故障恢复时间和审批人。密钥、token、客户订阅和原始业务数据不得进入证据包。

通过条件：TCP/UDP/客户协议样本符合预期；逐规则双向合计带宽与额度相互独立；计量差异在批准范围且可解释；暂停/删除/回滚/重启/控制中断均无端口串线、无静默丢量、无状态清空；容量停止点和适用硬件明确；开放事件已处理。

真实环境未执行前，`RELEASE.json` 必须继续保留 production VPS、容量和端到端协议为 unverified，`productionReady=false`。
